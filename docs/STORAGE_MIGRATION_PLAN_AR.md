# خطة ترحيل التخزين من Volume محلي إلى مزود S3-compatible

## الحدود

لا توجد عملية ترحيل مفعّلة في هذا الإصدار ولا يتم رفع أي ملف إلى خدمة خارجية.
النماذج وواجهات API تستخدم واجهة Django Storage، وتبقى مفاتيح الملفات الحالية
بدون تغيير كي يكون التحول قابلًا للرجوع.

## خطوات الترحيل المعتمدة

1. أعلن نافذة صيانة وجمّد الكتابة والرفع مؤقتًا.
2. خذ نسخة متسقة ومشفرة من PostgreSQL ومن Volume المحلي، ثم تحقق من checksums.
3. أنشئ Bucket **خاصًا** ومفاتيح محدودة الصلاحيات لموارد التطبيق فقط.
4. أضف adapter عامًا ومختبرًا للتخزين S3-compatible ثم ثبّت الاعتماديات في
   `requirements.lock` ومرّر مراجعة أمنية مستقلة.
5. نفّذ أداة ترحيل أولاً في dry-run؛ التصميم المستقبلي المقترح هو:

   ```sh
   python manage.py migrate_storage --from=local --to=s3 --dry-run
   ```

6. ارفع الملفات مع الحفاظ على object keys الحالية، وسجل count وsize وSHA-256
   لكل ملف، مع failure manifest قابل لإعادة التشغيل.
7. طابق عدد الملفات والأحجام والـchecksums بين المصدر والوجهة، واختبر القراءة
   والتنزيل المحمي وصلاحيات كل دور على بيانات اصطناعية.
8. غيّر الإعداد صراحة إلى `STORAGE_BACKEND=s3` وأضف متغيرات `S3_*` العامة فقط؛
   لا يوجد endpoint افتراضي أو مزود مفترض.
9. انشر صورة immutable، راقب الأخطاء والـreadiness، ونفّذ Smoke tests.
10. احتفظ بالـVolume المحلي read-only خلال فترة rollback المتفق عليها. لا تحذفه
    قبل قبول الترحيل النهائي وتمرين استعادة من التخزين الجديد.

## معيار rollback

إذا ظهرت اختلافات checksum أو رفض وصول أو ارتفاع أخطاء تنزيل، أعد
`STORAGE_BACKEND=local` في صورة متوافقة، وأبق مفاتيح الملفات كما هي. لا تستخدم
reverse migration لقاعدة البيانات لهذا التحول إلا بعد خطة منفصلة ومختبرة.
