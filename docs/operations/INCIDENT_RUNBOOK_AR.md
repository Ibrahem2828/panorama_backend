# دليل الاستجابة للحوادث

| الحادث | الإجراء الأول |
| --- | --- |
| readiness/startup 503 | أوقف الترقية، افحص DB/Redis/migrations/media mount من سجلات Coolify دون أسرار. |
| زيادة 5xx | ثبّت request_id، خفف الترافيك إن لزم، قارن آخر image digest، وابدأ rollback عند تحقق الأثر. |
| worker/queue متوقف | افحص broker وworker health وqueue lag، ثم أعد الخدمة بشكل متحكم به؛ لا تشغّل beat ثانيًا. |
| تسريب سر مشتبه | ألغِ السر وفق دليل التدوير، راجع audit/log access، ولا تنشر القيمة في التقرير. |
| تلف بيانات أو media | أوقف الكتابة، احفظ الأدلة، استعد إلى بيئة معزولة أولًا، ثم اتبع دليل restore. |

لكل حادث: owner، وقت الاكتشاف، request/correlation IDs المنزوعة الحساسية، الأثر، القرار، والدروس المستفادة.

## حماية الحسابات: قفل الدخول، عمر التوكن، وأحداث التدقيق

**قفل الدخول لكل حساب** (`apps/accounts/lockout.py`): بعد `LOGIN_LOCKOUT_THRESHOLD` (افتراضي 10) محاولة فاشلة متتالية للمعرّف نفسه (بريد/هاتف بعد التطبيع) خلال `LOGIN_LOCKOUT_WINDOW_MINUTES` (15) يُقفل الدخول `LOGIN_LOCKOUT_MINUTES` (15) بغض النظر عن عنوان IP. الرد أثناء القفل 429 مع `Retry-After` و`retry_after_seconds`، وحتى كلمة المرور الصحيحة ترفض أثناءه. العدّاد يُطبّق على المعرّفات غير الموجودة أيضًا (مفتاح مُجزّأ) فلا يكشف وجود الحساب. يُصفَّر العدّاد عند دخول ناجح أو إتمام إعادة تعيين كلمة المرور أو فك القفل من الداشبورد. الحالة في Redis (cache)، فإعادة تشغيل Redis تفك الأقفال. المقايضة المقبولة: من يعرف بريد ضحية يستطيع إبقاءها مقفلة بالرشّ المستمر، وللتخفيف يفكّ الموظف القفل.

**فك القفل (موظف):** `POST /api/v1/dashboard/users/{id}/unlock-login/` (صلاحية إدارة المستخدمين، وبشرط أعلى رتبة من الهدف) ويُسجَّل `account_login_unlocked`. تعديل العتبات عبر المتغيرات أعلاه فقط؛ في بيئة e2e القفل معطّل فعليًا ما لم يُضبط `LOGIN_LOCKOUT_THRESHOLD`.

**عمر Access Token:** الافتراضي صار 15 دقيقة (`JWT_ACCESS_TOKEN_LIFETIME_MINUTES`، كان 60) والـ Refresh 14 يومًا مع التدوير. تسجيل الخروج يضع Refresh في القائمة السوداء فقط، فيبقى Access الحالي صالحًا حتى 15 دقيقة كحد أقصى؛ أما تغيير/إعادة تعيين كلمة المرور وتغيير الدور وتعطيل الحساب فترفع `session_version` وتُبطل الـ Access فورًا. `last_login` يُحدَّث عند تسجيل الدخول.

**أحداث التدقيق الجديدة (بلا بيانات شخصية: معرّفات وقيم مقنّعة فقط):** `account_locked` (صف واحد عند القفل للحسابات الموجودة فقط، لا صف لكل محاولة فاشلة ولا للمعرّفات المجهولة)، `account_login_unlocked`، `password_changed`، `password_reset_completed`، `user_registered`، `student_profile_updated` (أسماء الحقول المتغيرة فقط)، إضافةً إلى `account_deletion_requested/cancelled` (صارت داخل نفس المعاملة). لا يُسجَّل حدث لكل دخول ناجح لتفادي ضخامة الجدول؛ يكفي `last_login`.

**الرقم الجامعي والتوثيق:** الرقم الجامعي فريد بين الحسابات الحية (قيد قاعدة بيانات جزئي `unique_active_student_number` + تحقق في الواجهة). الترحيل `accounts.0006` يفشل برسالة واضحة إن وُجدت تكرارات حالية (يجب حلها يدويًا قبل `migrate`). الطالب المعتمد أو صاحب الطلب المعلّق لا يستطيع تقديم طلب جديد (409 برمز `VERIFICATION_ALREADY_APPROVED` / `VERIFICATION_ALREADY_PENDING`)؛ لإعادة فتح طالب معتمد يستخدم الموظف قرار «يحتاج تحديث» على طلبه المعتمد.
